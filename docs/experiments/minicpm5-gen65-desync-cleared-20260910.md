# gen65「状态不连续」调查结案：无脱同步，冻结是门饿死的又一实例

日期：2026-09-10 晚｜分支：`codex/wayfinder-minicpm5-qes-faithful`
对象：`goooinext` seed 20260913 跑（300 代诊断线）在 gen65 的翻转与其后的永久冻结。

## 结论（一句话）

**没有引擎/状态脱同步。** 冻结的中心 `dd25f0c8`（记录侧拼写）在另一台机器（`gooo`）的全新引擎、全新进程里被精确复现：acc **0.5250**（在跑内四次读数同为 0.525）、Generation KL Error **2.0595957755521828**（与在跑内 gen65–68 的读数**逐位相同**）。gen65 的翻转是**真实的地形变化**（gen64 的一步 moved=331 落在一个随机 32 处改码代价更大的点上），而其后的冻结是**逐侧非劣门的平方放大饿死**——与 v3 起步三次崩塌同一失效类。**该 blocker 解除，W8A8 战役可以开跑。**

## 证据链

1. **翻转跨进程存活**（排除 KV/前缀缓存污染与引擎瞬态）：gen66 在原进程复现 −0.043；gen67/68 由**重启后的新进程**（新引擎、计数器归零）复现 −0.043/−0.032。
2. **kernel_compare 全程逐位相等**（排除值级脱同步）：gen63–68 每代引擎 dump vs 离线导出 1008 张量 `all_bitwise_equal=True`、0 mismatch。
3. **raw_mismatches 是平稳趋势不是断点**：893→903→…→1008→1047→1077（约 +13/代），对应已知的 0↔8 表示通道（`value_mismatches` 全程为 0）；gen67/68 计数归零（23/55）只是重启后 seen-coordinates 重置。
4. **新鲜引擎重放**（判别实验，`gooo`，`~/minicpm5-gen65replay/`，复用冻结 Runner 与在跑代码）：
   - q0 锚：acc 0.5000、KL 2.13458 —— 与在跑 gen0（0.5000）和冻结基线 2.1346 一致；
   - 中心 `state.json`（gen69 持久化、codes 20,491 处）：acc **0.5250**、KL **2.0595957755521828**（逐位）。
5. **哈希拼差不改权重**：在跑内哈希 `dd25f0c8…` vs 重放进程内哈希 `413fcc73…` 的差异**正是当日修掉的空桶 bug**——v1 `sha256` 计入空层桶而 `delta_map()` 丢弃；本地验证 v1 代码下加一个空桶即改变哈希（0e515f98→edfd9d05）。功能等价由 acc+KL 的精确复现兜底。

## 对 gen65 事件本身的复盘

- gen63/64 健康（M=25、d 均值 +0.0077/+0.0100）；gen64 的步 moved=331 产生 `dd25f0c8`，该状态本身确实更好（0.5083→0.5250）。
- 在该状态周围，随机 32 处改码的代价从典型 −2.3 抬升到约 −4.0（50 候选 0/50 非负、d 均值 −0.0401）。50 均值的 5 点位移 ≈ 18 SEM 排除的是**抽样噪声**，不排除「状态依赖的地形变陡」——后者正是事实。
- 逐侧 τ=0.02 门要求两侧同时 ≥ −0.02：逐侧合格率跌到 ~6%/3% 后平方放大 → qp=0 → 梯度空 → `moved=0` → `no_accept`×2 停机。
- **与 v3 起步三次崩塌同属一个失效类**：「门的存在让搜索存续依赖于候选分布恰好不过门」。
